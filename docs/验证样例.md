## 2. seekdb 表结构与索引（证明用到向量 + 全文能力）

**命令**
```sql
SHOW CREATE TABLE vault.chunks;
SHOW INDEX FROM vault.chunks;
```
**真实输出**
```sql
CREATE TABLE `chunks` (
  `chunk_id` bigint(20) NOT NULL,
  `note_id` bigint(20) NOT NULL,
  `seq` int(11) NOT NULL,
  `heading_path` varchar(768) DEFAULT NULL,
  `content` text DEFAULT NULL,
  `page_start` int(11) DEFAULT NULL,
  `page_end` int(11) DEFAULT NULL,
  `char_count` int(11) DEFAULT NULL,
  `emb` VECTOR(512) DEFAULT NULL,
  PRIMARY KEY (`chunk_id`),
  KEY `idx_chunks_note` (`note_id`) BLOCK_SIZE 16384 LOCAL,
  FULLTEXT KEY `ft_chunks_content` (`content`) WITH PARSER ik PARSER_PROPERTIES=(ik_mode="smart") BLOCK_SIZE 16384,
  VECTOR KEY `vidx_chunks_emb` (`emb`) WITH (DISTANCE=L2, TYPE=HNSW, LIB=VSAG, M=16, EF_CONSTRUCTION=200, EF_SEARCH=64, SYNC_MODE=ASYNC) BLOCK_SIZE 16384
) ORGANIZATION HEAP DEFAULT CHARSET = utf8mb4 ROW_FORMAT = DYNAMIC COMPRESSION = 'zstd_1.3.8' BLOCK_SIZE = 16384 TABLET_SIZE = 134217728 PCTFREE = 0 LOB_INROW_THRESHOLD=78643
```
```
key=PRIMARY            col=chunk_id  type=BTREE
key=idx_chunks_note    col=note_id   type=BTREE
key=ft_chunks_content  col=content   type=FULLTEXT     ← ik 中文全文索引
key=vidx_chunks_emb    col=emb       type=VECTOR       ← HNSW/VSAG 向量索引
```

要点：
- `emb VECTOR(512)` —— seekdb 原生向量列。
- `FULLTEXT ... WITH PARSER ik (ik_mode="smart")` —— 中文分词全文索引。
- `VECTOR ... WITH (DISTANCE=L2, TYPE=HNSW, LIB=VSAG, M=16, EF_CONSTRUCTION=200, EF_SEARCH=64)` —— 近似最近邻索引。
- `ORGANIZATION HEAP` —— 堆表，利于向量/全文扫描。

## 3. 混合检索是**单条 SQL、库内融合**（非客户端拼接）

这是本项目的核心约束。检索时下发给 seekdb 的**就是一条 SQL**，全文相关度与向量距离在库内加权融合排序：

```sql
SELECT
    c.chunk_id, c.note_id, n.rel_path, n.course, n.course_code, n.lecture_no, n.kind,
    n.title, c.heading_path, c.page_start, c.page_end, LEFT(c.content, 220),
    l2_distance(c.emb, %s) AS dist,
    MATCH(c.content) AGAINST (%s) AS rel,
    (1-%s)*MATCH(c.content) AGAINST (%s)/(1+MATCH(c.content) AGAINST (%s))
        + %s*(1/(1+l2_distance(c.emb, %s))) AS score
FROM chunks c JOIN notes n ON n.note_id = c.note_id
ORDER BY score DESC LIMIT %s
```
> 融合公式：`score = (1-α)·rel/(1+rel) + α·1/(1+dist)`，α 为向量权重（默认 0.5）。结构化过滤（课程/类型/讲次）以 `WHERE` 下推到**同一条** SQL。

### EXPLAIN 实测（证明索引与融合都在库内完成）

**① 纯全文检索**（`WHERE MATCH(content) AGAINST('deadlock')`）→ 命中 ik 全文索引：
```
|0 |TOP-N SORT           |                         |3   |3427|
|1 |└─TEXT RETRIEVAL SCAN|chunks(ft_chunks_content)|107 |3425|
     calc_relevance=true, pushdown_match_filter(MATCH(chunks.content) AGAINST('deadlock'))
```

**② 纯向量检索（精确）** `ORDER BY l2_distance(emb,'[...]') LIMIT 3` → 精确 TOP-N：
```
|0 |TOP-N SORT       |      |3    |1433|
|1 |└─TABLE FULL SCAN|chunks|(全表)|1226|
```

**③ 纯向量检索（近似）** 加 `APPROXIMATE` → 命中 HNSW 向量索引，估算耗时降到 **9µs**（≈150×）：
```
|0 |VECTOR INDEX SCAN|chunks(vidx_chunks_emb)|1|9|
```

**④ 混合检索单条 SQL** → 一次 `MERGE JOIN` + 融合打分 `TOP-N SORT`，`sort_keys` 中同时含 `MATCH(...)` 与 `l2_distance(...)`：
```
|0 |TOP-N SORT         |                  |3    |...
|1 |└─MERGE JOIN       |                  |...  |...
|2 |  ├─TABLE FULL SCAN|n                 |(全表)|...
|3 |  └─TABLE FULL SCAN|c(idx_chunks_note)|(全表)|...
   sort_keys([ ... MATCH(c.content) AGAINST('两阶段锁的死锁怎么检测和处理') ...
               + l2_distance(c.emb, '[...]') ... , DESC]), topn(3)
```

> 注：`EST.ROWS` 为本机完整索引的物理估计，与公开子集口径不同，故隐去具体数值；**算子结构（TEXT RETRIEVAL SCAN / VECTOR INDEX SCAN / MERGE JOIN）与融合 `sort_keys` 即为「库内一次融合」的证据**。

**结论**：全文相关度与向量距离在**同一条 SQL、同一个 TOP-N SORT 算子**内融合，客户端只发一次查询、只收一份已排好序的结果——不存在“先各自取回再在浏览器/服务层拼接”的情况。

> 设计取舍：当前 `search.py` 走向量**精确** TOP-N（②），在万行级规模下快且结果精确；如需超大规模可加 `APPROXIMATE`（③）启用 HNSW 近似检索。ik 全文索引在纯全文/`WHERE MATCH` 路径（①）已被优化器实际选用。

## 5. HTTP API 样例（curl + 真实 JSON）

> ⚠️ **Windows Git Bash 编码坑**，中文查询有两种正确发法：
> 1. **推荐（跨平台稳）**：把中文预先百分号编码成纯 ASCII，**直接写进 URL 字符串**（下面各例即此形式，可整行复制）。
> 2. 或在 **UTF-8 shell**（Linux / macOS / WSL）里用 `curl -G --data-urlencode 'q=中文原文'`。
>
> **两个反例（都会拿到乱码或错误结果）**：① 在 GBK 的 Git Bash 里 `--data-urlencode 'q=中文原文'`——控制台先把中文转成 GBK 字节；② 对**已编码**的值再用 `--data-urlencode`——`%E4` 被二次编码为 `%25E4`，服务端只解一层，得到字面量 `%E4...`（实测会返回 `query="%E4%B8%A4..."` 且命中垃圾结果）。
