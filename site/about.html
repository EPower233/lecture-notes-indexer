核心：混合检索在 seekdb 单条 SQL 内完成

全文相关度 MATCH() 与向量距离 l2_distance() 在同一条 SQL 内加权融合排序， 结构化过滤（课程 / 类型 / 讲次）也在同条 SQL 下推——绝不把向量检索与全文检索拆到客户端拼接。

score = (1-α) · rel/(1+rel) + α · 1/(1+dist)
  rel  = MATCH(c.content) AGAINST (%s)  -- ik 全文相关度，自然语言模式
  dist = l2_distance(c.emb, %s)       -- 512 维向量 L2 距离
  α    = 向量分权重（默认 0.5，前端可调）

两个分量各自归一化到 (0,1) 再加权，避免全文分（无界）与向量分（距离）量纲冲突。 全文侧用 NATURAL LANGUAGE 模式而非 BOOLEAN 模式：ik 对查询侧自动分词，中文召回显著更好 （BOOLEAN 模式下"版本链"这类复合词召回为 0）。

建表 DDL（节选）

CREATE TABLE vault.chunks (
  chunk_id BIGINT PRIMARY KEY, note_id BIGINT, seq INT,
  heading_path VARCHAR(768), content TEXT,
  page_start INT, page_end INT, char_count INT,
  emb VECTOR(512),
  FULLTEXT INDEX ft_chunks_content (content) WITH PARSER ik,
  VECTOR INDEX vidx_chunks_emb (emb) WITH (DISTANCE=l2, TYPE=hnsw, LIB=vsag)
) ORGANIZATION = HEAP;

EXPLAIN 证据：确实用上了向量与全文索引

以下为对 live seekdb 实测 EXPLAIN 的结果，证明融合发生在数据库内、且命中专用索引：

查询形态执行计划算子说明 / 实测
WHERE MATCH(content) AGAINST(…) TEXT RETRIEVAL SCAN(ft_chunks_content) 命中 ik 全文索引，calc_relevance=true
ORDER BY l2_distance(emb,…) LIMIT TOP-N SORT + TABLE FULL SCAN 精确 KNN（无 ANN），EST.TIME ≈ 1433µs；万行级数据下结果最准
ORDER BY l2_distance(emb,…) APPROXIMATE LIMIT VECTOR INDEX SCAN(vidx_chunks_emb) 启用 HNSW 近似，EST.TIME ≈ 9µs（约 150× 提速）；超大规模时的可选优化
混合融合（本项目默认） MERGE JOIN + 融合分 TOP-N SORT 单条 SQL 内完成向量分与全文分的融合排序——in-DB fusion 的直接证据

seekdb v1.4.0.0（MySQL 协议） Docker Desktop · 宿主 20881→2881 VECTOR(512) + HNSW(vsag) FULLTEXT · ik smart BAAI/bge-small-zh-v1.5 FastAPI + pymysql 原生 HTML/CSS/JS 前端 Qoder 全程开发

嵌入模型 bge-small-zh-v1.5（512 维、CPU、归一化）本机运行；查询侧加前缀 "为这个句子生成表示以用于检索相关文章：" 以匹配该模型的检索指令。 seekdb 部署在 Windows Docker，宿主端口取 20881——因为 Windows Hyper-V 保留了 TCP 2791–2890，2881/2886 无法在宿主绑定。

为什么用 seekdb 而非 PowerContext

赛题要求"实质性使用 seekdb 或 PowerContext"。二者定位不同： seekdb 是 AI 原生向量+关系混合数据库，正是本项目"讲义混合检索"的直接底座； PowerContext 是面向 Agent 的跨会话上下文/记忆服务（Memory/Handoff/Experience），解决的是"工作交接时上下文丢失"， 与"文档检索"不是同一问题，硬接入只会增加依赖而无产品价值。 故本作选 seekdb，并把它用在最能体现其价值的地方——单 SQL 向量+全文融合、EXPLAIN 可证。

本机运行（复现完整在线检索）

# 1) 启动 seekdb（Docker，宿主端口 20881）
docker start seekdb
# 2) 建表
mysql -h127.0.0.1 -P20881 -uroot < schema.sql
# 3) 入库（解析 vault + 向量化）
py -3.10 ingest.py
# 4) 起服务（含前端 /ui）
py -3.10 -m uvicorn serve:app --host 127.0.0.1 --port 8000
# 打开 http://127.0.0.1:8000/ui/
